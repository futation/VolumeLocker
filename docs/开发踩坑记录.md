# 开发踩坑记录 —— VolumeLocker 的设计决定与实测教训

> 这份文档是 VolumeLocker 开发过程中沉淀下来的技术笔记:为什么这样设计、哪些坑是
> 真机实测踩出来的。每一条背后都对应一次真实的翻车或一组客观数据。
> 如果你想改控制律、动界面或自己打包,建议先读对应章节——很多坑从表面上看
> "程序运行正常",只有数据能暴露问题。

---

## 先看架构

```
volume_locker.py     主程序:托盘、GUI、多设备管理、COM 生命周期、控制环调度
loudness_limiter.py  控制律(纯逻辑,零 Windows 依赖、可离线测)
volume_limiter.py    音量标尺换算(百分比 <-> dB 查表)+ peak_to_dbfs
theme.py             外观层:DPI 感知、调色板、字体阶梯、ttk 样式、深浅主题
widgets.py           自绘控件(Canvas):电平表、状态药丸、折叠标题条
```

分层是刻意的,两条依赖纪律贯穿始终:

1. **`loudness_limiter.py` 不 import 任何 Windows 库** —— 控制律的全部行为都能
   离线验证(47 项断言,秒级跑完),而不是靠耳朵在实时音频上逐个试。
2. **`theme.py` / `widgets.py` 不 import 音频库** —— 没插音频设备时界面照样能
   构建起来。

两种工作模式(`MODE_LIMIT` / `MODE_LOCK`)共用同一个音量标量,所以**同时开必然
互相打架**——这也是程序把它们做成互斥单选的原因。

## 一、控制律:三个不可动摇的设计决定

### 1. 控制量是"输出响度",不是"信号峰值"

```
output_dbfs = signal_dbfs + current_volume_db      # 输出响度
```

这个公式看起来是常识,但掉进去一次才知道有多深:**Windows 峰值表读的是音量
衰减之前的信号**(Microsoft Learn 对 Peak Meter 的定义)。也就是说,压完音量
之后,表上的读数**不变**。

如果拿信号峰值直接跟阈值比,会发生什么:安静段 → 峰值低于阈值 → 把音量放回
上限 → 爆炸来了 → 再压下去 → 表值还是那个峰值 → 又放回去……音量来回横跳,
听感退化成"以音量为基准的锁定"。

**推论:绝不靠回读表值来判断"我有没有生效"。** 只写不验,生效与否由公式保证。

### 2. 攻为瞬时、放为缓慢、放有地板

```
volume_max = min(ceiling - signal_dbfs,     # 瞬时(抓瞬态)
                 ceiling - env_dbfs)        # 滑动均值(稳态不呼吸)
```

由 `output = signal + volume <= ceiling` 直接推出,没有 base_volume 项。
三个分支的实测教训:

- **攻(压制)**:直接夹到 `volume_max`,无速率限制,一拍内完成(控制环 8ms
  节拍)。给攻击加斜率只会让第一个瞬态漏出去。
- **包络**:不能用"上升立刻跟随"——那会跟踪信号波峰而不是平均响度,算出的
  稳态压制深度比均值深 **8 dB 以上**(实测 volume 被压到 −28.3 dB,均值对应的
  正解是 −17.7 dB)。必须用滑动均值。
- **释放与瞬时钳位会互相打架**,这是整个控制律里最容易"直觉性改错"的地方:
  - 把释放写成 `volume += rate*dt`,每次音乐起伏都会把音量瞬时夹回深处,
    释放只能从那里再挪一点——实测释放速率被压到 **0.06 dB/s**(配置 1.5,
    慢 25 倍);
  - 于是改成 `min(volume, 上一拍值)`,结果引入**棘轮**:音量单调下滑永不回升,
    摆动恶化到 19.5 dB。
  - **两个方向都试过,都更糟。** 当前结构(先夹紧再释放)是经过验证的那个,
    别再动。
- **迟滞判定** `_inhibit` 的判据要用**信号量**:`signal_dbfs + base > ceiling`
  开闸门,`hold_dbfs` 与 `ceiling - current_volume_db` 比迟滞。第一版写成
  `hold_dbfs + volume > ceiling`,算术上永远够不到阈值,迟滞形同虚设——而且
  表面看起来一切正常(占比 0% 这种异常只有打了统计才能发现)。
- **静音分支不能早退**:峰值低于阈值时若直接 return,保持期与释放逻辑根本
  走不到,素材一停就"秒放"。必须把 0 喂给限幅器继续走流程。
- **时间基准必须只有一套**:一处传 `perf_counter()` 绝对值、另一处传从 0 起算
  的相对值,`hold_until` 会被设成大数,**永不释放**。

### 3. 输出滤波是非对称的,而且只许磨平"写出去的值"

`volume_filter_seconds`(默认 0.05)只过滤**向上**(回升)的下发值,向下
(压制)直接放行——双向都滤会拖慢攻击,得不偿失。

这块埋过整个项目最隐蔽的一个 bug:**反馈量与滤波基准必须是两个量**。
控制律里"释放"是在上一拍的命令值上加 `release×dt`,而滤波的基准是上次真正
下发的值。如果把"滤波后的下发值"当反馈喂回去,释放会被滤波**再乘一次**
`a = dt/(tau+dt)`——等效释放速率被偷乘:

| tau | 有效释放(配置 1.5 dB/s) | 爆炸之后恢复 |
|---|---|---|
| 0.00 | 1.50 dB/s | 3.5 s |
| **0.05(默认)** | **0.21 dB/s** | **25 s** |
| 0.10 | 0.11 dB/s | 30 s 后还差 2.6 dB |

更坏的是副作用:它让"音量平滑"这个滑条**看起来在控制恢复速度**——完全不是
它该干的事。改成"命令值反馈"后,各 tau 的恢复都回到 3.5~4.9 s,滤波只磨平
写出去的值:

| tau | 摆动(1Hz 起伏素材) | 恢复 |
|---|---|---|
| 0.00 | 2.08 dB | 1.0 s |
| 0.40 | **0.90 dB** | 1.7 s |
| 0.80 | 0.55 dB | 2.6 s |

所以滑条上限取 0.5:再大只是在磨最后一点抖动,却开始付恢复时间的代价。

三种反馈选择放在一起的实测后果,给后来者避坑:

| 反馈量 | 后果 |
|---|---|
| 真正写出去的值 | 被写入节流卡住变陈旧,释放量每拍算成同一个数,音量永远爬不回来 |
| 滤波后的下发值 | 释放被滤波再乘一次,恢复要 25 秒(上表) |
| **限幅器上一拍的命令值(现用)** | 每拍都更新、不被节流、不被滤波缩放,恢复只由 release 决定 |

这条结构自带一条不变量:**`sent <= target` 恒成立**(向上朝 target 靠近并夹住,
向下等于 target)⇒ 写出去的值永不高于控制律允许的上限 ⇒ **滤波只会让声音更
安静、不会更响**。回归测试里"恢复速度与 tau 无关"断言的就是这个。

## 二、Core Audio / pycaw 实战陷阱

这些是平台行为或物理约束,全部真机实测:

1. **COM 指针不能跨线程用**(实测 `access violation`)。meter/volume 接口
   指针必须在**使用它们的线程**里创建;另起线程要自己 `CoInitializeEx`。
2. **`IAudioClient::Initialize` 的 format 参数不能传 `None`**;同一个 client
   不能二次 Initialize(`0x88890002`)。每次要重新 `Activate`,并且用
   `QueryInterface` 而不是直接 `cast`(后者会拿到错 vtable → "无效指针")。
3. **峰值表按设备周期刷新**(实测连读 6000 次值不变,约 10ms 一次)。控制环
   节拍小于它**没有收益**,只是白耗 CPU。
4. **pycaw 的两个坑**:新版 `AudioDevice` 没有 `AudioMeterInformation` 属性;
   它自带的 `IAudioMeterInformation` 声明不全。本项目自己声明了完整的
   `IAudioMeterInformationFull` vtable,经 `IMMDevice::Activate` 取。
5. **音量范围是端点属性,不是常量**。本机实测(Realtek,`GetVolumeRange()`
   = −65.25..0 dB):写 −50/−60 都精确生效,写 **−70 直接 COMError
   E_INVALIDARG**——设备**拒绝**,不是夹住。这决定了产品里的两层保险:
   任何写入目标先夹到端点真实范围内;上限滑条下限与最大衰减量联动。
6. **硬件音量步长因设备而异**:Realtek 0.031 dB,蓝牙耳机实测 0.5 dB。
   蓝牙 AVRCP 的写入即时生效、读回即新值(198µs/次),但这依赖具体耳机,
   换耳机需要重测。
7. **独占模式绕过一切**:`ISimpleAudioVolume` 等会话音量接口对独占流无效
   (Microsoft 文档明确)。foobar2000 WASAPI 独占、ASIO、Kernel Streaming
   都不受控——这是"用改音量实现限幅"这条路线的固有边界。

## 三、GUI:三层分离与 ttkbootstrap 的暗坑

界面分三层,**颜色只出现在第一层**:

| 层 | 文件 | 职责 |
|---|---|---|
| 1 | `theme.py` | **颜色的唯一来源**:DPI 感知、调色板、字体阶梯、ttk 样式、深浅主题 |
| 2 | `widgets.py` | Canvas 自绘控件:电平表、状态药丸、折叠标题条 |
| 3 | `volume_locker.py` | 只排版。颜色走 `theme.color("...")` 或命名样式 |

**硬规则:主程序里不许出现字面色值。** 冒烟测试用正则扫**整个文件**(不是只
扫当时在改的函数——这条规则本身就是漏网之鱼教出来的:浅色模式下好好的颜色,
切深色变成"白底白字",只能靠眼睛逐个发现,机器扫一遍五秒钟)。

ttkbootstrap 的几个实测暗坑,每一个的表现都是"静默"的:

1. **未注册的 `style=` 名字会被静默丢弃。** 写错样式名不报任何错,控件实际
   拿到默认样式,**颜色悄悄不对**。对策:主题层把所有注册过的名字记进
   `theme.style_names`,冒烟测试逐个核对界面代码里的每个 `style=`。
   把静默降级变成硬失败,是这个项目 GUI 测试最重要的一条。
2. **文档里的样式未必存在。** `bootstyle="round-toggle"` 照官方文档抄,实测
   `TclError: Layout not found` 直接崩在启动——对一个托盘程序,表现为
   "双击没反应"。任何 ttkbootstrap 特性先用探针脚本验证再进产品代码。
3. **`theme_use()` 会重置全部样式定义**。自定义样式必须**先切主题、再配置**,
   顺序反了自定义色会被主题色覆盖。
4. **控件"坐在哪个表面"要显式声明**。滑条轨道、单选圆点、进度条槽都是按
   表面烘出来的**图片**:坐在卡片里的控件必须声明卡片表面
   (`bootstyle="@card"`),否则按窗口底色烘图,在卡片上留一块对不上的底色。
   而且只加表面声明**还不够**——ttkbootstrap 只重烘图片,不管控件自己的
   `background`,必须同时把该表面样式的 `background` 配成卡片色。
   验收方式是**量像素**:抓控件 bbox 打印竖直剖面,确认轨道上下两段都等于
   卡片色,而不是看截图。
5. **`ttk.Progressbar` 的槽也是图片**,`troughcolor` 等配色选项全改不动。
   项目里的"当前设备音量"细进度条因此是 Canvas 自绘的。
   **结论:凡是"槽/轨道/指示器"类元素,ttk 主题多半用图片,别指望配色选项。**
6. **下拉框的亮底是"聚焦高亮"不是背景**。readonly 状态下一聚焦整块变亮,
   必须显式 `style.map("TCombobox", selectbackground=[("readonly", 卡片色)])`。
   它只在聚焦时出现,不聚焦时看不出来——很容易以为没问题。
7. **符号字形要过一遍**:`▶`(U+25B6)在 `Microsoft YaHei UI`(中文 Windows
   上 Tk 的默认字体)和 `Segoe UI` 里都没有字形,渲染成方框。同样不可用的
   还有 `▸ ► ▷ ◀ ◂ ◄ ▾ ⇒ ➤`;可用的是 `▲`(U+25B2)/`▼`(U+25BC)/`→`/`»`。
   冒烟测试会遍历界面文字查所有非 CJK 符号的字形。
8. **电平表配色以"响度上限"为基准,不是满刻度**。第一版按 −60..0 配色,
   −6 dBFS 的正常输出把大半条染成黄红,看着像一直在报警。改成:下限→上限
   走完绿→琥珀,一越线就是纯红。颜色表达的是"离你设的上限还有多远"。
9. **"隐藏后再显示"的控件必须用 `pack(before=...)/pack(after=...)` 固定
   位置**,否则会排到所有已有控件后面,出现"设置跑到底部去了"的错位。

还有一个和库无关但更致命的教训:**死代码比它看起来危险得多**。一段初始化
代码被插进函数中间后提前 `return`,后半段全部成了死代码——后果不是立刻崩,
而是一条长链:启动即异常 → 轮询线程静默退出 → 整个软件"看起来在运行但什么
都不做"。对策:GUI 冒烟测试用 AST 审计所有源文件里"return/raise/continue/
break 之后还有语句"的函数;界面刷新出错只记日志,绝不顺手停掉控制环线程。

## 四、打包成单文件 exe 的四个坑(PyInstaller onefile)

1. **onefile 是父子两个进程。** 引导进程解包并起子进程跑 Python,**窗口和
   托盘都属于子进程**。两个后果:
   - 从外面找窗口/托盘必须搜**整棵进程树**,只按启动 PID 找永远找不到;
   - 只杀父进程 → 应用还在后台跑,而且**锁住 exe**,下次打包会
     `PermissionError [WinError 5]`。
2. **windowed 模式下 `sys.stdout` 不是 `None`,而是一个 NullWriter**——
   `print()` 全部静默丢弃(实测重定向到文件也是 0 字节)。冻结版必须一律把
   stdout/stderr 接到日志文件(行缓冲 + 按大小轮转)。**这是打包版唯一的
   排查入口**,不是可选项。
3. **ttkbootstrap 有 20+ 个运行时资源**(元素图片、manifest)。少了界面会
   **静默**降级。它自带 PyInstaller hook,再 `collect_data_files` 兜一层。
4. **`missing module named comtypes.gen` 是正常的**(comtypes 运行期才生成),
   别去"修"。设备枚举、接口 Activate、音量写入在冻结环境里全部正常。

**图标单独说**:一个只改了扩展名的 PNG(`.ico` 后缀、PNG 内容)能同时骗过
两个检查——`iconbitmap()` 对它**照样不报错**(窗口图标静默失效),PIL 读不出
ICO 时**静默**退回内置兜底图。而单尺寸大图在托盘里会糊:托盘 16px、任务栏
32px、资源管理器大图标 256px,各档都要写进同一个多尺寸 ICO,并且**生成后立刻
读回来验证档位是否齐全**。

构建验收要端到端:本项目 `tools/verify_exe.py` 对冻结版 exe 跑 26 条客观断言
(窗口/托盘/图标/日志/COM 枚举/限幅器写音量/自启模式不弹窗仍工作/用户配置未
被触碰/真实音量已恢复)。"构建成功但双击没反应"才是打包的典型失败模式。

## 五、参数与听感诊断顺序

| 参数 | 默认 | 说明 |
|---|---|---|
| `ceiling_dbfs` | −6.0 | 输出响度上限,范围 −60..0 dBFS |
| `release_db_per_s` | 5.0 | 回升速率。**泵动的主旋钮**:周期 ≈ 压缩深度 ÷ 释放速率 |
| `hold_seconds` | 0.0 | 压制后保持。太小会让对白被抽 |
| `volume_filter_seconds` | 0.05 | 下发音量低通(非对称),只磨平写出去的值,**不影响恢复速度** |
| `release_threshold_db` | 1.5 | 释放迟滞死区 |
| `detector_seconds` | 0.30 | 滑动均值窗口,决定稳态跟得多慢 |

**为什么上限最低只能到 −60、不能再低**:限幅是靠写音量实现的,能被压到的
输出下限 = 音量下限 + 信号。信号最强是 0 dBFS ⇒ 需要写到的最深音量**等于
上限本身**(见第二节第 5 条:低于端点下限的写入会被设备拒绝)。上限滑条
下限、最大衰减量、电平表刻度下限这三个数必须联动改,少一个都会出现"拖到最
底也压不到那条线"或"写入被拒那一拍等于没写"。

听感不对时按这个顺序调:

1. **"一炸一炸"** → 调 `release_db_per_s`(往小),这是唯一管恢复节奏的旋钮;
   想在不减慢恢复的前提下压抖动,把 `volume_filter_seconds` 往大调
2. **音量细碎抖动(单拍跳变)** → `volume_filter_seconds` 往大
3. **压下去后回不来** → 只由 `release_db_per_s` 和 `hold_seconds` 决定,
   别去动滤波(历史上这曾是滤波 bug,已修,别再让滤波背锅)

## 六、已知限制(物理上限,不是 bug)

- **独占模式绕过一切**(见第二节第 7 条)。
- **蓝牙 AVRCP 行为依赖具体耳机**,换耳机要重测写入延迟与读回行为。
- **"用改音量实现限幅"是包络级压制,不是样本级限幅。** 回路带宽(8ms 节拍
  ≈ 125Hz)远低于音频带宽(20kHz),单个样本内的过冲挡不住。零过冲需要把
  限幅器做进信号链(采集环回 + look-ahead + 虚拟声卡 / APO),那是另一套
  架构。
- **WASAPI loopback 测不了"响度真的降了"**:环回采集在音量节点**之前**,
  实测两趟峰值完全相同。这一项只能靠耳朵。

## 七、验证策略(为什么测试长这样)

1. **控制律独立成纯逻辑模块**是所有测试的地基:47 项不变量(超限必压、低响度
   零干预、保持、释放、静音、base≠0 时上限仍是绝对 dBFS 上限、滑条最严端真的
   压得到)全部离线秒级跑完。
2. **期望值必须从控制律推导,不要手算硬编码数字。** 手算错过四次,每次都表现
   为"测试失败但代码是对的"——后来全部改成按定义推导。
3. **测试只覆盖一个基准值时,任何"相对该基准"的错误都会隐身。** 上限公式
   多算一个基础音量的 bug 藏了很久,因为当时的测试恰好全在 base=0 工况下跑
   ——base=0 恰好让错误项消失。修完后补了 base ∈ {0, −6, −10.58, −20} 的
   矩阵用例。
4. **GUI 测试要做到"看不到窗口也能验"**:界面截成 PNG(浅/深 × 面板开合,
   可灌假数据看电平表);改配色/排版跑脚本自查,而不是靠人肉截图。
5. **凡会 attach 到真实端点、或让控制环跑起来的脚本,结束时必须把音量恢复
   原值**——测试改了系统音量又没恢复,轻则污染后续测试,重则让下一次测试
   得出完全错误的结论(实测踩过:一次集成测试被另一个正在运行的音量锁定
   程序污染,误判为"蓝牙设备会把音量弹回")。
6. **挂 GUI 主循环的工具必须有硬超时**,调用私有方法前先 `getattr`——否则
   一次方法改名就是"工具永久挂死、进程空转、一张图不出"。
